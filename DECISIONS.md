## 2026-08-16 — Revert the client from Python back to Go (compiled binary)

- **Context:** After actually deploying the pure-Python client to a real target host (`AHHome-Ubuntu-Server`) and confirming `--selftest`/`--install-service` both work correctly, the user raised a concrete objection: a plaintext, directly-readable `.py` file is too easy to de-obfuscate compared to the original compiled Go binary — "py太容易被反混淆了吧". This reopens the "Replace the Go client with a pure-Python client" decision from earlier today. A PyInstaller-repackaged Python binary was considered as a middle ground and explicitly rejected after discussion: PyInstaller bundles are decompiled back to near-original Python source relatively easily with public tools (`pyinstxtractor` + `decompyle3`), so it would *not* meaningfully restore the inspection resistance the Go binary had — it would give a false sense of security without the substance. User chose a full revert to Go instead, accepting the reintroduced Go-toolchain-on-the-generator-machine requirement as the cost of genuine binary opacity.
- **Decision:** The client goes back to being a compiled Go binary (`GOOS=linux` static build via `go build`, per-arch cross-compilation), restored from the pre-removal implementation in git history (commit `8707ffb`, the last commit before the Go client was removed) rather than retyped from memory, to avoid transcription bugs in the embedded template. The `--no-build`/`--arch` CLI flags return; the GUI gains equivalent controls (an architecture field, an "emit Go source only" checkbox) so GUI users have the same escape hatch CLI users always had. Everything unrelated to the client's implementation language is unaffected: the generator stays Python + PySide6, the GUI stays bilingual, and the generator's own packaging (`.deb`/`.exe` via PyInstaller) is untouched — only the *client's* tech stack reverts, not the generator's.
- **Rejected:** PyInstaller-packaging the Python client (see above — doesn't deliver real opacity, only a thin extra step, per this session's testing/discussion). Keeping the plain `.py` client (the option from the earlier decision) — superseded now that the user has weighed the tradeoff against real deployment experience and prioritized binary opacity over the convenience of not needing a Go toolchain.
- **Consequences:** The generator machine needs a Go toolchain again to actually compile a client binary (or `--no-build`/the GUI's "emit source only" checkbox to hand off compilation to any Linux box, as before the 2026-08-16 rewrite). `DESIGN.md`, `README.md`, and `STATUS.md` need to reflect Go as the client language again. This is the second reversal of the client's implementation language in one day — a sign the decision should be treated as settled going forward unless a genuinely new constraint appears; don't relitigate this without new information.

## 2026-08-16 — Bilingual (English/中文) GUI

- **Context:** User visually confirmed the PySide6 GUI runs correctly on a real Windows display (the first real, non-offscreen verification of it) and asked for Chinese-language support, "做成双语的" (make it bilingual), for the GUI itself — distinct from the project's existing docs bilingual convention (README/DESIGN already have English + `.zh.md` pairs).
- **Decision:** Added a `STRINGS` dict (`en`/`zh`) covering every GUI label, button, placeholder, and dialog string, plus a language dropdown in the window's top-left corner that live-retranslates the form via a `retranslate()` method (including dynamically-added mount rows, via `MountRow.retranslate()`). Default language is auto-detected from `QLocale.system().name()` (zh if the system locale starts with "zh", else English), user can switch at any time. `validate()`'s error messages (shared with the `--config`/`--cli` headless paths) stay English-only at the source; the GUI translates the known ones for its message box via a small `VALIDATE_MSG_ZH` lookup rather than refactoring the shared `validate()` function to be locale-aware — keeps the headless/scripted path's output stable for anything parsing it.
- **Rejected:** Full Qt Linguist `.ts`/`.qm` translation workflow (`pyside6-lupdate`/`pyside6-lrelease`) — rejected as overkill for a ~25-string form; would add a build step and tooling dependency for no real benefit at this size. Localizing `validate()` itself — rejected to avoid a shared function having two different message-format contracts depending on caller.
- **Consequences:** Adding new GUI strings in the future means updating both `STRINGS["en"]` and `STRINGS["zh"]` together, or the missing key throws a `KeyError` at `retranslate()` time — there's no fallback-to-English-if-missing. Terminal `--cli` prompts (`prompt_config()`) and `--help` text remain English-only; only the GUI got bilingual support, matching the user's request scope ("客户端GUI 双语，其他的让他们自己用cli").

## 2026-08-16 — Replace the Go client with a pure-Python client

- **Context:** User confirmed every deployment target for this project guarantees a Python environment. The Go client's stated advantage (single static binary, zero client runtime deps, small attack surface — see the earlier "Tech stack" entry in `DESIGN.md`) stops mattering once that guarantee holds, and it was actively costing usability: the generator (and previously, even `--no-build`) needed a Go toolchain just to produce or emit the client, and the client itself needed cross-compilation per target arch.
- **Decision:** The deployed mount client is now a plain Python 3.8+ script (no compilation step) using the `cryptography` package for AES-256-GCM decryption — the same crypto library and scheme (XOR-split key + AES-GCM) already used by the generator, so both sides share one dependency instead of two toolchains. The client checks for `cryptography` at startup and auto-installs it via `pip` if missing (mirroring the existing `apt-get install cifs-utils` auto-install already present in the mount logic). No per-arch builds: one script runs anywhere Python 3.8+ exists on Debian/Ubuntu Linux — no change to the "Debian/Ubuntu Linux only" non-goal, this is about the interpreter dependency, not the OS.
- **Rejected:** Keeping the Go client and only fixing the `--no-build` bug (previous session's fix, kept) — rejected because it still leaves a Go toolchain as a hard requirement somewhere in the pipeline for anyone who wants a genuinely compiled client, which no longer buys anything now that Python is guaranteed everywhere.
- **Consequences:** Client secrets now live in a plaintext-readable `.py` file on disk rather than inside a stripped/compiled binary — a real (if modest, per the existing "Security reality check" in the script's docstring — this was always obfuscation, not real secrecy against a root-privileged attacker) reduction in casual-inspection resistance. `DESIGN.md`'s tech-stack table, architecture diagram, and reproduction requirements need updating to match (tracked as a follow-up in this same work session). The `--arch` and `--no-build` generator flags are removed — there is no longer a build step to configure.

## 2026-08-16 — Give the generator a PySide6 GUI, keep the CLI path, ship as .deb/.exe via CI

- **Context:** User asked to turn the generator's config-collection step (currently `prompt_config()`, an interactive terminal prompt) into a GUI, packaged as installable `.deb` (Linux) and `.exe` (Windows), while the deployed mount client (see the entry above) stays CLI-only — it runs unattended via systemd, a GUI there would serve no purpose.
- **Decision:** Built the GUI with **PySide6** (Qt for Python), not PyQt — PySide6 is LGPLv3 (permits linking/distribution without forcing GPL on this Apache-2.0 project), while PyQt is GPL or paid-commercial dual-licensed, which would conflict with staying permissively licensed. The GUI is additive: `nas-enp-gen.py` launches the GUI when run with no arguments, keeps `--config <file>` for headless/scripted use, and adds `--cli` to force the old terminal-prompt flow on displays that can't run a GUI (bare SSH sessions, CI, etc.). PySide6 itself is auto-installed via `pip` if missing, same pattern as the `cryptography` check. Packaging uses PyInstaller to produce a single-file executable, wrapped into a `.deb` (via `dpkg-deb`, built and testable on this Linux host) and an `.exe` (via PyInstaller on a `windows-latest` GitHub Actions runner — this host has no Windows environment, so the `.exe` cannot be built or tested locally).
- **Rejected:** Tkinter — ruled out for the nicer/native look the user asked for, at the cost of a heavier bundled dependency (PyInstaller output grows from ~15-20MB to 100MB+). Building the `.exe` by hand on a separate Windows machine — rejected in favor of GitHub Actions CI so the build is automated, reproducible, and runs on a real Windows environment instead of relying on Wine-based cross-compilation from Linux (unreliable and unverifiable here).
- **Consequences:** New CI workflow triggers on version tags and must be validated once a real tag is pushed (untestable except by structure/lint review until then). The GUI's actual interactive behavior cannot be visually verified in this headless root shell — only import/construction can be smoke-tested with `QT_QPA_PLATFORM=offscreen`. `requirements.txt` gains `PySide6`; `pyinstaller` and packaging tooling are CI/dev-time only, not a runtime dependency of the generator or client.

## 2026-08-16 — Fix `--no-build` requiring a Go toolchain

- **Context:** `build()` in `nas-enp-gen.py` called `subprocess.run(["go", "mod", "init", ...])` unconditionally before the `if not do_build: return` branch, so the documented no-Go-toolchain path (`--no-build`) still required the `go` binary and failed with `FileNotFoundError` when it was missing. Verified on this host (no Go toolchain installed) both before and after the fix.
- **Decision:** Moved the `go mod init` call to after the `--no-build` early return, immediately before the actual `go build` loop where it's needed. `--no-build` now only writes `main.go` and prints manual compile instructions — no `go` binary required. Re-verified with `python3 nas-enp-gen.py --config config.example.json --no-build` on this Go-less host: succeeds.
- **Rejected:** Installing a Go toolchain on this host instead of fixing the code — rejected because that would only verify the primary build path, not fix `--no-build` for the users it's actually meant to serve (people without Go).
- **Consequences:** `--no-build` no longer needs Go on the generating machine. The primary `go build` path (non-`--no-build`) is still unverified on this host and remains a blocker for `v0.1.0` (see `STATUS.md`).

## 2026-08-16 — Normalize project to full-tier structure

- **Context:** Project existed as a flat folder (`nas-enp-gen.py`, `README.md`, empty `Design.md`, `config.example.json`, a prebuilt `nas-enp-mount` binary) with no `repo/`/`snapshots/` split, no git repo, no `.gitignore`, no lockfile. It has real config/secrets and is meant to be deployed to other machines, so it qualifies for full-tier per the project-management skill.
- **Decision:** Restructure into the standard `<project>/{repo,snapshots}` layout, add the full bilingual doc set (README/DESIGN in EN+ZH, CHANGELOG, STATUS, DECISIONS), `.gitignore`, `requirements.txt`, `git init -b main` with the `CharlesGool` noreply identity, and a GitHub remote.
- **Rejected:** Leaving it as a light-tier flat folder — ruled out because it has an `.env`-equivalent config file with real secrets and is designed for cross-machine deployment, both of which are explicit upgrade triggers in the skill.
- **Consequences:** All future work happens under `repo/`; releases go through the tag + snapshot process instead of ad hoc copying.

## 2026-08-16 — Strip real NAS credentials out of `config.example.json`

- **Context:** The pre-existing `config.example.json` at the project root contained the *real* production NAS credentials (a real internal host IP, a real account name, and a real password) for the NAS that backs this maintainer's local project storage — despite being named "example" and about to become a git-tracked file.
- **Decision:** `repo/config.example.json` now contains only placeholder values (`192.0.2.10`, `your-nas-user`, `your-nas-password`, generic paths). The real values were moved to `nas.local.json` at the project root (outside `repo/`, outside git, never committed) so the working config isn't lost. `config.json` (the name a user is instructed to `cp` to) is gitignored so future local configs never accidentally get committed either.
- **Rejected:** Keeping the real values in `config.example.json` and just gitignoring the file going forward — rejected because "example" files are expected to be safe to commit and to read; a gitignored file named "example" is a trap for the next person (or session) who forgets to check.
- **Consequences:** The prebuilt `nas-enp-mount` binary at the project root also embeds these real (encrypted) credentials and is likewise kept outside `repo/`/git for the same reason.

## 2026-08-16 — Go public under Apache-2.0

- **Context:** User asked to make the repo public. Sole runtime dependency (`cryptography`) is dual BSD/Apache-2.0, not vendored — no copyleft, no NOTICE-triggering obligations. Full-history and commit-metadata review found no leaked credentials in git history (the real NAS credentials were caught before the first commit, see the entry above); a real internal host IP, account name, and local absolute paths that had leaked into `DECISIONS.md`/`STATUS.md` prose were redacted before the repo went public.
- **Decision:** License the project under Apache License 2.0 (`LICENSE`, `README.md`/`README.zh.md` updated); flip the GitHub repo to public.
- **Rejected:** "All rights reserved" (public but no reuse license) — user preferred a permissive open-source license over restricting reuse. MIT was also offered — user chose Apache-2.0 for its explicit patent grant.
- **Consequences:** Third parties may now use, modify, and redistribute this code under Apache-2.0 terms, including commercially. Any future vendored third-party content must be checked for Apache-2.0 compatibility before being added.
