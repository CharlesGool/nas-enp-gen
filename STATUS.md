**In progress:** reverted the client from pure-Python back to a compiled Go binary (real deployment testing showed the plaintext `.py` client was too easy to inspect; a PyInstaller-repackaged Python client was considered and rejected as not meaningfully more opaque). Generator keeps its bilingual (English/中文) PySide6 GUI and `.deb`/`.exe` packaging — those are unaffected by the client-language reversal. GUI gained an arch field + "emit Go source only" checkbox to match the restored `--arch`/`--no-build` CLI flags. See `DECISIONS.md` 2026-08-16 entries for the full history (two reversals in one day — treat the Go client as settled).
**Next:** visually confirm the new arch/emit-source GUI controls on a real display (Windows or Linux); user still needs to build `dist/nas-enp-gen.exe` on their Windows machine and confirm it runs; then push a tag to dry-run the CI-built `.exe` before trusting it.
**Known issues:**
- no automated tests.
- **The real `go build` path is finally verified end-to-end on this dev host**: installed Go 1.18 via `apt-get install golang-go`, then ran the generator against `config.example.json` with real compilation (single-arch `amd64`, and multi-arch `amd64,arm64` cross-compile) — output is a stripped, statically-linked ELF binary, `--selftest` and `--help` both work correctly on it. `--no-build` source emission was re-verified too. This closes a gap that had been open all session.
- **Real NAS mounting is confirmed working** — the user deployed the (then still pure-Python) client to a real host (`AHHome-Ubuntu-Server`), ran `--selftest` and `--install-service` successfully. The restored Go client uses the identical mount/retry/systemd logic (ported from the same pre-removal Go source, recovered verbatim from git history commit `8707ffb`), so this should still hold, but hasn't been re-run against a real NAS with the *Go* binary specifically yet.
- GUI's base form has been visually verified on a real Windows display by the user. The bilingual language switcher and the new arch/emit-source controls have only been offscreen/logic-tested here (`QT_QPA_PLATFORM=offscreen`), including a forced-failure test of the build-error path (Go missing → `QMessageBox` shown, no crash) — none of this has been visually re-confirmed by the user yet.
- `.exe` **generator** installer build is CI-only (`windows-latest` via `.github/workflows/release-installers.yml`) and has never actually run — unverified until a real tag is pushed. The user's local Windows build attempt via `pyinstaller packaging\nas-enp-gen.spec` hasn't completed yet (their first attempt used the wrong invocation, `python pyinstaller ...`; corrected instructions are in the README).
- `.deb` **generator** installer build was tested locally end-to-end in an earlier session pass (~67MB, `dpkg -c` confirmed file layout) — unaffected by this client-language revert, not re-tested in this pass.
- The client binary is per-user (embeds that user's own encrypted config) and is *not* something that can be pre-built and attached to GitHub Releases generically — only the generator's own `.deb`/`.exe` installers are shippable release assets. Documented in the README now.
**Blocked on:** a successful local or CI Windows `.exe` build, visual confirmation of the GUI's new controls on a real display, and a real NAS mount test specifically with the restored Go binary (the Python-client mount test doesn't carry over as proof for the Go one, even though the logic is identical). Do not cut `v0.1.0` until those are done.
